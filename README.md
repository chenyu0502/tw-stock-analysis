### 為什麼要有 `api/` 這一層

台股資料來源（證交所、櫃買中心、Yahoo Finance）都不允許瀏覽器直接跨域呼叫。
常見做法是繞經公開 CORS proxy，但那些 proxy 不穩定、有流量限制，且會看到全部請求內容。

這個專案改由自己的伺服器端直連上游：

- 開發時由 `vite-plugin-local-api.js` 掛在 dev server 的 `/api/*`
- 正式環境由 Vercel 把 `api/*.js` 部署成 serverless function

兩邊呼叫的是同一份 `handlers.js`，不會出現只在其中一邊會壞的問題。

### 函式執行區域：一個設定同時綁住兩件事

Vercel 專案的 Function Region（Settings → Functions）是可以改的，Hobby 方案可選一個。
但它同時決定了兩件互相拉扯的事：

| 需求 | 方向 |
|---|---|
| 台股上游（證交所、櫃買、Yahoo）都在台灣 | 區域離台灣越近越快 |
| Gemini API 依來源 IP 判定地區，不服務部分地區 | 區域必須落在 Google 服務的範圍內 |

踩過的坑完整記在這裡，因為它的症狀有誤導性：

1. 原本在美東 `iad1`。台股上游要橫跨太平洋，實測單次查詢 25.5 秒（本機 0.02 秒），
   十次取樣裡個股報價有四次完全拿不到。
2. 為了解這個問題改到香港 `hkg1`。台股資料確實變快了，**但 AI 分析全部回 400
   「User location is not supported」**——Gemini 不服務香港。而且其他功能都正常，
   只有 AI 頁壞掉，很容易誤判成金鑰或程式問題。
3. 改到東京 `hnd1`，兩個條件同時成立，目前採用。

**改區域前務必確認新區域不在 Gemini 的排除名單內。** 改完之後 Vercel 不會自動重新部署，
要到 Deployments 手動 Redeploy 才會生效。

（README 先前寫「Hobby 方案固定跑在美東 iad1，無法更改區域」，那句話是錯的，
也是這次誤判的起點之一。）

### 均線參數回測

「回測最佳化」掃描 68 組短長均線組合，以只做多的交叉策略回測，選出報酬率最高者。

實作上的兩個取捨：

1. **用隔日開盤價成交，不用當日收盤價。** 訊號要到當日收盤才成立，若以當日收盤價成交
   等於用了未來資訊，會高估績效。
2. **候選參數刻意不做全範圍暴力搜尋。** 組合數過多會嚴重過度配適，選出的參數對未來沒有意義。

最大回檔採逐日結算帳面權益，不是只在平倉時取樣。只看平倉會讓一組全部獲利出場的參數
算出零回檔，但持倉期間可能經歷過三成的帳面虧損，那才是實際交易時會讓人出場的數字。

回測結果同時顯示買進持有報酬率作為對照組。策略贏不過買進持有就沒有使用價值。

## 價格型態

`src/lib/patterns.js` 由擺盪轉折點的相對位置判定型態，沿用 `levels.js` 已經算好的
那組轉折點。**不經過語言模型**——交給模型的問題不只是慢與貴，而是它會為了回答
而硬套一個名稱，同一份資料每次跑還可能給出不同答案，無從查核。

高點與低點各自的走向決定通道類型態：

```
高點抬高 ＋ 低點墊高  → 上升通道
高點降低 ＋ 低點下移  → 下降通道
高點降低 ＋ 低點墊高  → 收斂三角
高點抬高 ＋ 低點下移  → 擴散喇叭
高點齊平 ＋ 低點齊平  → 箱型整理
```

頭肩與雙重頂底另外判定，因為它們看的是特定幾點的相對高度，不是整體走向。

**型態判讀本質上主觀，誤判率高，因此刻意保守：條件不明確就回「型態未明」，不硬湊。**
一個誠實的「看不出來」比一個似是而非的「頭肩頂」有用得多。
每個結論都附上構成它的實際轉折點與日期，可以在圖上核對。實例：

```
3231  頭肩底
  左肩 2026-06-26 的 153.00、頭部 2026-07-14 的 139.00、右肩 2026-07-30 的 157.50；
  兩肩高度相差在 3% 內，頭部低於肩部 10.1%
```

門檻集中在 `PATTERN_THRESHOLDS`。放寬會讓型態變多但誤判也變多，
收緊則多數標的都會是「型態未明」。

一個實作上的坑：`minPivots` 一度設為 4，結果**最典型的 W 底與 M 頭永遠判不出來**——
那是「高、低、高」的三點結構。需要更多點的型態（通道與三角形各需兩個高低點）
由各自的判定函式自行把關即可。

## 均線攻守狀態（二日法則）

`src/lib/stance.js` 判定價格相對均線處於什麼狀態。與 `crossState` 的差別是**時序**：
那個回答「兩條均線目前誰在上面」，這個回答「跌破第幾天了、確認了沒有」。
同樣是跌破均線，第一天與確認後的意義完全不同，前者常是假跌破。

```
收盤跌破均線當天      → 跌破觀察中（第 1 天，僅警戒）
隔日最低價再破前低    → 跌破確認
隔日最低價未破前低    → 跌破未確認（多半是洗盤）
突破反之，看最高價
```

三個實作上的決定：

1. **只認收盤價的穿越，不看盤中觸及。** 盤中戳破均線再拉回極為常見，
   用那個判定會讓狀態一天到晚跳動，失去參考價值。
2. **短、長均線分開判定，不合成單一結論。** 兩者常給出不同狀態，
   而那個分歧本身就是資訊，硬合成會把它抹掉。
3. **只描述狀態，不給動作。** 參考站在同樣的狀態下會顯示「執行動作：減碼／觀望」，
   本站不做這件事——那是投資指令，與「程式算數字、不下買賣指令」的原則衝突。
   要不要因此加減碼是使用者的決定。狀態的敘述一律附上觸發它的實際數值，
   單元測試也會檢查敘述中不得出現「建議」「減碼」「停損」這類字眼。

**這是常見的交易慣例，不是被證明有效的方法。** 它的價值在於把「跌破」拆成
可驗證的階段，而不是宣稱能預測方向。是否真的有效，可以用現有的回測引擎去驗。

以 2330、18/52 均線與參考站對照，兩套獨立實作得到相同結果
（短期 `WATCH_BREAKDOWN`、長期 `BEARISH_CONFIRMED`，均線值同為 2357.50）。

### 二日法則到底有沒有用：對照組要選對

`compareStanceStrategies()` 用與 `indicators.js` 相同的回測約定
（隔日開盤成交、逐日結算最大回檔、同一組手續費）跑三種做法。

**關鍵是對照組不能只有買進持有。** 二日法則本質上是在均線訊號上多加一道確認，
要回答的問題是「那道確認有沒有讓結果變好」；只跟買進持有比，
會把均線本身的效果誤算成二日法則的功勞。因此一律同時列出「單純均線」。

2330 近一年的實際結果：

| 均線／做法 | 報酬率 | 交易 | 勝率 | 最大回檔 | 持倉比例 |
|---|---|---|---|---|---|
| 18 日 · 二日法則 | +74.8% | 4 | 50% | -12.4% | 92% |
| 18 日 · 單純均線 | +34.2% | 15 | 33% | -19.6% | 73% |
| 52 日 · 二日法則 | +50.0% | 3 | 67% | -11.7% | 89% |
| 52 日 · 單純均線 | +20.8% | 10 | 20% | -16.7% | 89% |
| 買進持有 | +87.3% | | | | |

兩件事同時成立：**那道確認確實有加分**（交易次數少了七成、回檔更小、報酬更高），
但**兩者都輸給什麼都不做**。這正是這個功能該給的答案——
不是替指標背書，而是讓使用者看到它在自己的標的上實際表現如何。

### 期初部位不能只認穿越事件

回測一開始只在偵測到穿越時才進場，結果一檔從頭到尾都在均線之上、
期間從未跌破的股票會全程空手、報酬掛零，把一個順風的走勢算成沒有績效。
**穿越是狀態的「轉換點」，不是狀態本身**，因此起點若已站上均線就視為持有中。
這個缺陷是被單元測試抓出來的，不是靠審視程式碼發現的。

### 狀態要在收合的清單上就看得到

狀態一開始只放在展開後的區塊裡，結果是**持有二十幾檔時等於看不到**——
不會有人為了看狀態一張一張點開。因此改到卡片的標題列，掃一眼整份清單即可。

代價是歷史 K 線得整批載入，而不是展開時才抓。這個取捨可以接受：
上游是 Yahoo 與證交所，沒有額度限制，伺服器端也有快取。
法人買賣超則維持延後載入——那個走 FinMind，免費方案每小時 600 次，
一次替所有卡片抓會很快用掉額度，而它只有展開時才顯示。

清單上的標籤把**持續狀態調暗、事件狀態上色**：

```
2330   空頭排列 · 18/52MA   短·跌破觀察   長·跌破確認    ← 兩個都上色
0056   空頭反彈 · 20/60MA   短·均線上     長·均線上      ← 調暗
2317   空頭排列 · 20/60MA   短·跌破確認   長·均線下      ← 混合
```

二十幾檔裡多數會停在均線上或均線下，那是常態不是訊息；全部上色等於沒有重點。
完整敘述放在 `title` 屬性，滑鼠停留即可看到。

## 體質評分：六個面向，分數可拆解

`src/lib/health.js`，**不經過語言模型**，與 `levels.js`、`risks.js`、`peers.js` 同性質。

參考站有這個功能，但本站是**另行設計而非複製**——沒有它的計分規格，硬湊一套再稱為複製
只是腦補。因此全部門檻都是本站自訂的校準值，集中在 `RUBRIC` 與 `WEIGHTS` 裡，不是什麼公認標準。

| 面向 | 權重 | 看什麼 |
|---|---|---|
| 獲利能力 | 20 | ROE、淨利率、淨利率相對去年同期的變化 |
| 成長動能 | 20 | 月營收年增（近三月權重 0.6、單月 0.4） |
| 財務結構 | 10 | 負債比 |
| 股利政策 | 10 | 連續配發年數、配發率是否落在合理區間 |
| 趨勢位置 | 20 | 120 日均線方向、現價相對長期均線 |
| 估值水位 | 20 | 自身歷史分位與同業分位，越便宜得分越高 |

四個設計上的決定：

1. **分數必須可拆解。** 回傳的不只是總分，而是每個面向的得分、權重，以及觸發那個得分的
   **原始數值**。一個把十幾項壓成單一數字卻不能展開的分數，就是另一個黑箱。
2. **燈號描述體質強弱，不是買賣建議。** 本站不給買賣指令，這條規則同樣適用於燈號——
   好公司也可能買在很差的價位。四級為強健（≥ 75）、健康（60–74）、普通（45–59）、
   偏弱（< 45）。

   配色依使用者指定：強健琥珀、健康綠、普通灰、偏弱紅。**這組顏色與台股漲跌色是
   相反的**（本站紅代表上漲、綠代表下跌，見 `changeColor`），因此燈號一律連同文字
   標籤顯示，絕不只用顏色表示等級——少了文字，紅色燈號會被讀成「今天漲」。
   顏色集中在 `format.js` 的 `healthColor`，清單上的小標籤與 AI 頁的面板共用同一份
   定義，兩處不會各自漂移。
3. **缺資料不等於體質差。** 缺項不給零分，而是從分母移除，另外回報涵蓋率。
   總分是「可評面向的加權平均」，不是「得分除以滿分」——後者會讓 ETF 天生偏低，
   把資料不適用誤讀成體質不好。涵蓋率低於 50% 時不給等級，數字也改稱「可評項目得分」。
4. **短線指標完全不計入。** KD、MACD、RSI 回答的是「現在在什麼位置」，不是「這家公司
   好不好」。放進體質分數會讓分數每天跳動，失去體質該有的穩定性。

計分用分段線性插值而不是跳階：ROE 從 9.9% 變成 10.1% 不該讓總分跳好幾分，
否則分數會隨每季財報無意義地大幅震盪。

以六種側寫驗證鑑別力（這些是合成資料，用來檢查分數不會全部擠在中段）：

| 側寫 | 總分 | 燈號 | 涵蓋率 |
|---|---|---|---|
| 績優成長股 | 85 | 強健 | 100% |
| 穩定高配息電信 | 61 | 健康 | 100% |
| 金融股 | 62 | 健康 | 100% |
| 獲利衰退傳產 | 20 | 偏弱 | 100% |
| ETF（有配息紀錄） | 71 | 資料不足 | 30% |
| ETF（無財報無配息） | 71 | 資料不足 | 20% |

### 燈號要在清單上就看得到，而財報必須排隊載入

燈號顯示在持股頁與分析頁的個股名稱旁邊。兩頁共用 `StockCard`，因此只加在一處。

但體質分數需要財報，而**一檔要打五個 FinMind 資料集**。每張卡各自去抓，二十幾張
就是上百個上游請求同時送出——免費方案每小時 600 次，開兩次頁面用掉大半，而且那種
請求形狀正是先前把函式打到逾時的那一種。這與 `RiskScan` 面對的是同一個問題，
那裡的解法是改成按鈕觸發。

這裡不能用按鈕：使用者要的是「一眼看到」，預設空白的燈號等於沒做。因此改成
`useHealthScores` 統一排隊：**一檔落地才送下一檔**，燈號由上往下陸續出現。
載入失敗也會前進——`marketSlice` 的 rejected 會把 `{ available: false, reason }`
寫進對應的鍵，佇列不會卡在一檔取不到的標的上。伺服器端財報快取 24 小時，
因此這個排隊只有每天第一次開頁時會感覺到。

歷史 K 線不排隊：它走 Yahoo 與證交所，沒有額度限制，分析頁本來就是整批載入。

**趨勢面的公式必須與 AI 頁完全相同。** 清單只需要現價與 120 日均線兩樣，
為了一顆燈號跑整套指標是浪費，因此另有 `trendInputFromCandles`；但它的現價取
最後一根收盤價（與 `computeLevels` 的 `price` 同源）、斜率取近 20 日變化率，
與 `buildAnalysisInput` 逐字一致。否則同一檔在清單與 AI 頁會算出不同分數，
而那正是這個專案一路在修的那種「兩頁數字對不上」。

### 一個已知會失真的項目

**負債比對金融業沒有意義。** 銀行與保險公司的負債比天然在 90% 以上，那是業務模式而不是
財務風險——合成的金融股側寫在這一項拿 0 分，拖低總分約六分。權重因此刻意壓到最低的
10 分，介面也註明。要正確處理得引入產業分類另立一套標準，成本與效益不成比例。

## 估值與風險：程式算，模型不碰

`api/_lib/fundamentals.js` 與 `src/lib/risks.js` **完全不經過語言模型**。
理由與 `levels.js` 不讓模型產生價位相同：這些是可逐項查核的算術，
交給模型只會得到看似合理卻對不上的數字，而且每次跑還不一樣。

### 估值看的是自己的歷史分位，不是絕對值

「本益比 30 倍」對不同產業意義天差地遠，「本益比高於自己過去五年 85% 的時間」
則是同一檔跟自己比，跨標的都成立。因此估值一律以分位呈現：

```
本益比 27.8 倍　歷史 77.0% 分位（區間 12.5～34.9，中位 23.4，樣本 1213 個交易日）
```

介面只陳述位置，不下「偏貴」「便宜」的結論——那是投資判斷，由使用者自己做。
系統指令禁止模型給買賣指令與目標價，這條規則一併適用於估值。

### 但只看歷史分位有盲點，所以再加一個橫向座標

歷史分位有一個系統性的死角：**整個產業一起重評價時，個股的歷史分位會長期停在高檔，
看起來永遠很貴**；產業結構性衰退時反過來，看起來永遠便宜。只有縱向座標，
分不出「這檔貴」與「這個產業貴」——而這兩件事的意義完全不同。

因此 `api/_lib/peers.js` 補上橫向座標：以同產業其他公司為基準的本益比、
股價淨值比與殖利率統計。

```
本益比 20.0 倍　同業 42.9% 分位 · 第 7／14 名（同業中位 21.5，四分位 15.5～26.0）
```

幾個刻意的取捨：

1. **不列產業龍頭，改列估值鄰居。** 免費資料源沒有市值，用成交值代替會在冷門股
   身上失真。「本檔上下各五檔是誰」對「這檔落在同業的哪一段」這個問題更直接。
2. **名次一律由低至高。** 本益比第 1 名是全產業最低，不是「最好」，
   因此名次永遠與指標名稱一起顯示，不單獨呈現。
3. **虧損公司沒有本益比就明寫「本檔無此數值」**，不顯示 0，也不留白。
   前者會被讀成「本益比極低」，後者看起來像載入失敗。排序時這類公司排在最後，
   否則當成 0 會排到最前面，看起來像全產業最便宜的一檔。
4. **同業家數少於 5 家時照樣顯示數字，但先標明不具代表性。**
   三家公司的中位數幾乎等於任一檔的值，「高於同業中位數」這句話沒有資訊量。
5. **ETF 與受益證券直接回「不適用」**，不是「查無資料」。它們沒有可比較的本業，
   而訊息講不清楚會讓人以為是抓取失敗而反覆重試。

資料成本幾乎為零：產業分類走 FinMind `TaiwanStockInfo`，一次取回全市場、快取一天；
估值數字直接重用 `/api/valuation` 已經抓好的全市場快照，不另外打上游。
共用同一份快照還有一個正確性上的理由——分開抓可能讓「本檔估值」與「同業中位數」
落在不同的交易日。

### 財報是單季數

FinMind 的 `TaiwanStockFinancialStatements` 為**單季**值（已實測：2026 Q2 營收
等於四至六月的月營收加總，分毫不差），因此近四季相加即為 TTM，
不需要做累計數相減。搞錯這一點會讓 TTM EPS 差好幾倍。

利潤率取最近一季而非 TTM，並一律附上去年同期作為對照。
孤立的毛利率數字看不出好壞，有同期比較才知道是在改善還是惡化。

ROE 的分母採期初與期末權益的平均。只用期末會在現金增資後把 ROE 壓低到失真，
取不到期初值時退回期末並在介面標示口徑。

股利要先依年度加總才能算年配息與配發率——季配息的公司一年有四筆，
FinMind 的 `year` 欄位是「114年第2季」這種格式。

### 風險提示採固定門檻

每一條都是門檻判斷，輸入相同就得到相同結果，而且**每一項都附上觸發它的實際數值**，
使用者可以自行驗證，也可以不同意。門檻集中在 `THRESHOLDS`，調整時不必翻遍整個檔案。

顯示精度必須與門檻對齊：分位顯示曾四捨五入到整數，84.7% 會顯示成 85%，
而門檻正是 85，畫面上就出現「已達 85% 卻沒有提示」的矛盾。現已改為顯示到小數一位。

模型自行提出的疑慮另外放在「AI 判讀的盲點」，與這份清單分開，
因為兩者的可信度完全不同。

### 全部位掃描

規則型偵測原本只在 AI 頁的單一標的上跑。持有二十幾檔時等於看不到——
沒有人會為了確認有沒有觸發規則而一檔一檔點開。這與「均線攻守狀態原本藏在展開區」
是同一個問題：**功能做對了，位置讓它等於不存在**。

`RiskScan` 放在持股頁，一次跑完所有持股，只列出有觸發的，依嚴重度排序。

預設只用**畫面上已經載入的資料**（報價、融資融券、法人當日、歷史 K 線），不額外發請求。
估值分位與財報那幾條需要 `/api/fundamentals`，一檔要打五個 FinMind 資料集，
因此改為按鈕觸發，按鈕上寫明會查幾檔。實測五檔持股：
載入前觸發 1 項，載入基本面後增為 4 項。

三種狀況必須分清楚，不能混為一談：

| 狀況 | 呈現 |
|---|---|
| 跑過了，沒觸發 | 不列出，標題顯示「N 檔皆未觸發」 |
| 歷史股價不足 60 日 | 技術面規則跳過，footer 說明有幾檔 |
| ETF 沒有信用交易／財報 | footer 註明「無資料不是無異常」 |

### 融資融券的異常規則

五條門檻判斷，**只陳述事實，不標多空方向**：

```
融資暴增     單日 +500 張以上 且 增幅 > 20%
融券暴增     單日 +200 張以上 且 增幅 > 30%
資券同增     兩邊增幅皆 > 10%
資增券減     融資 > +3% 且 融券 < -20%
融券大量回補 單日減少 > 200 張
```

**張數與增幅要同時達標。** 只看張數會讓大型股天天觸發（融資餘額本來就數萬張），
只看增幅則小型股一點風吹草動就報警。

參考站把「資增券減」標為「偏多訊號」，本站不這樣寫。融資暴增有人讀成散戶追高、
有人讀成資金流入，沒有共識；把其中一種解讀寫死在介面上等於替使用者做了判斷。
單元測試會檢查訊息中不得出現「偏多」「偏空」這類方向性字眼。

參考站的「資增券減」也沒有幅度門檻，於是「融資多一張、融券少一張」也算數——
實測五檔就有兩檔觸發，等於天天在響，因此本站加上幅度要求。

### 除息提醒

除息當天股價**必然**扣除配息金額，帳面市值同步下降。這與其他風險不同——
它不是「可能會不好」，而是「一定會發生」。不知情的人會把它讀成下跌，
但錢只是還沒到，實際撥付約在除息後一個多月。

資料來自證交所的除權除息**預告表** `TWT48U` 與櫃買的 `tpex_exright_prepost`，
涵蓋已公告的區間（實測約往後兩個月）。這與權益曲線用的 `TWT49U` 是不同的表：
那個是**結果表**，只有已經發生的，用途是還原歷史淨值。

三個實作重點：

1. **金額可能尚未定案。** 證交所在該欄位放的是「待公告實際收益分配金額」，
   而且帶 HTML 標籤。此時金額為 `null`，介面寫「待公告」——
   **不可當成零**，那會讓人以為這次不配息。
2. **只提醒 30 天內的。** 預告表涵蓋兩個月，但兩個月後的除息現在不需要注意，
   全列出來只會把真正接近的那幾檔淹沒。門檻是 `THRESHOLDS.exDividendWithinDays`。
3. **發放日要另外查。** 見下一節。

#### 發放日不在預告表裡

證交所與櫃買的預告表都只給除息日。那兩張表的用途是除息當天的參考價計算，
不是股利撥付，因此沒有發放日這一欄。發放日要到 FinMind 的
`TaiwanStockDividend` 才有（`CashDividendPaymentDate`）。

`/api/exdividend` 因此接受可選的 `codes`，對其中**確實有即將除息**的那幾檔補上發放日。
兩個成本控制：

- 全市場清單本身不分代號、共用同一份快取，發放日在那之後才併上去，
  不同的 `codes` 不會各自重建一份全市場清單。
- 只查「在清單中且真的要除息」的代號。持有二十幾檔時，同一個月要除息的通常只有幾檔，
  對全部持股查是白費 FinMind 額度。實測四檔持股中三檔有除息時，只發出三次查詢。

**以除息日為鍵取發放日，不是取最近一筆。** 月配 ETF 一年有十二次配息，
取最近一筆會把上一次的發放日安到這一次頭上——而那個日期看起來完全合理，
錯了也不會有人發現。對不上就留白顯示「待公告」，寧可沒有也不要給錯的。

沒有 `FINMIND_TOKEN`、查詢失敗、或公司尚未公告發放日時，一律顯示「待公告」，
其餘欄位完全不受影響。

提醒放在**持股頁**而不只是個股分析裡。除息影響的是整個帳戶：
持有十幾檔月配 ETF 時，光看單一檔看不出「這個月會有幾次、總共領多少」。
持股頁的橫幅會列出即將除息的持股、發放日、每股金額與依股數估算的總額；
個股層級的提醒則併入 AI 頁的風險清單。

### 第二層：讓模型做綜合敘述

數字定案之後，才把它們交給模型寫一段解讀。模型拿到的是**已經算好的結果**，
不是原始資料，因此沒有機會自己算錯——這與支撐壓力的分工完全一致。

輸出多了兩個欄位：

| 欄位 | 內容 |
|---|---|
| `valuation` | 兩個座標軸各自的等級與依據、綜合等級、撐住或壓抑估值的因素、觀察條件 |
| `riskSummary` | 把已偵測風險串成一段，指出哪一項最需要注意 |

`valuation` 的結構刻意把兩個座標軸拆開，而不是壓成一段敘述：

```
綜合          中性
相對自己歷史  偏高   本益比位於自己五年 72.4% 分位，高於中位 16.2 倍
相對同業      偏低   同業中位 21.5 倍，本檔 20.0 倍，由低至高第 7／14 名
撐住或壓抑估值的因素
  · 毛利率 31.2%，較去年同期 28.9% 改善，往上撐
  · 月營收年增 18.3%，往上撐
```

**兩軸訊號相反時介面會另外標出來**，而且那個判斷由程式做，不依賴模型記得提——
兩軸相反正是最值得注意的情況，摺在一段敘述裡會被讀過去。

四條額外的約束寫進系統指令：

1. **不可自行計算、推估或修改任何數字**，需要提到時只能原樣引用。
2. **兩個座標軸要分開判斷，不可用其中一邊的數字去解釋另一邊。**
   歷史分位高但同業分位低，代表整個產業一起重評價；歷史分位低但同業分位高，
   代表這檔相對同業並不便宜，只是自己曾經更貴。遇到這種情形必須明講。
3. **估值等級不是買賣建議。** 綜合等級要同時考慮兩軸與獲利表現——
   高分位若有獲利成長支撐，與高分位卻伴隨獲利衰退，意義完全不同。
4. **風險綜述只能引用已列出的項目，不得新增。**
   模型自由發揮的風險另外放在「AI 判讀的盲點」，兩者的可信度不同，不混在一起。

另外兩條寫在同業比較上：產業分類是粗分類，同一分類內的規模與產品結構可能差異極大，
橫向結論必須說明這個限制；標示家數不足時不得用那組中位數下結論。

沒有對應資料時（ETF 沒有財報、也沒有可比較的本業）該軸的等級一律填「資料不足」，
而不是讓模型憑印象猜。

送進提示詞的基本面在 `buildFundamentalSummary()` 就先壓縮過，
只留分位、利潤率、營收年增這些敘述用得到的欄位。
完整回應含四分位、十二個月營收序列與六年股利明細，那些是給圖表用的，
整包送出只會膨脹 token，也增加模型從中挑數字的機會。

**成本**：併進原本那一次呼叫，不新增請求次數。系統指令由 582 字元增為 921，
responseSchema 由 1,891 增為 2,459，整體增幅約三成——與事前評估相符。

### 多模型輪流嘗試必須有總時間預算

加上備援鏈之後出現 `504 FUNCTION_INVOCATION_TIMEOUT`：函式執行滿 60 秒
被平台中斷，前端拿到的是**沒有任何訊息的錯誤頁**，
使用者無從得知是額度用完、上游忙碌還是網路問題。

原因是逾時會相加。原本 `timeoutMs: 45000, retries: 3` 單一模型最壞就要 180 秒，
再乘上四個模型更不可能收斂——只是原本備援極少觸發，所以沒有浮現。

因此 `fetchWithRetry` 增加 `deadline`（整段流程的絕對截止時間）：
每次嘗試只能用剩餘時間，退避也吃預算，不夠就直接放棄而不是送出一個注定被截斷的請求。
`generateJson` 以 `TOTAL_BUDGET_MS = 50000` 開場，並在每換一個模型前檢查剩餘時間。

同一個模型**不重試**：備援鏈本身就是重試，而且是更好的重試。
對忙碌或已無額度的模型再敲一次多半還是失敗，卻要付出一次完整的等待；
換一個模型則有真正的機會成功。生成逾時更不該重試——慢代表它需要更多時間，
再送一次只會更慢。因此逾時與忙碌也列為換模型的條件。

總預算 52 秒、單一模型 48 秒。這兩個數字調過三次，過程值得記下來：

| 設定 | 結果 |
|---|---|
| 45 秒 × 3 次重試 × 4 個模型 | 乘積遠超過 maxDuration，`504` 無訊息中斷 |
| 28 秒 × 1 次重試 | 504 消失，但門檻卡在生成時間上，把正常請求切斷 |
| 48 秒 × 不重試 | 時間集中給當下的模型 |

實測一次成功的生成需 25 至 39 秒。輸出本身只有九百多字元並不大——
慢的是結構化輸出的約束解碼，跟提示詞長度關係不大，所以縮短提示詞沒有用。

單模型逾時要逼近總預算，不要刻意保留一段給下一個模型：
**保留的時間若不足以完成一次生成，等於兩個模型都拿不到足夠的時間**。
真的用完就誠實回報，而不是再開一個注定失敗的嘗試。

實測（以永不回應的上游模擬最壞情況）：總耗時 48 秒，在上限之內且留有回應餘裕；
四個模型全部配額用盡時 0.0 秒走完整條鏈，各送出一次請求。

### 免費層的真正限制是每日次數，不是錢

實測 `gemini-3.7-flash` 免費層為**每日 20 次**，用完後回 429 `RESOURCE_EXHAUSTED`。
token 費用為零，但這個次數對實際使用相當緊。

**配額是按模型分別計算的**，因此配額用盡時換一個模型就能繼續。
原本的備援 `gemini-flash-latest` 對這件事完全無效——它是別名，
指向的往往就是剛失敗的那一個模型，落在同一個額度桶裡。實測：

```
gemini-3.7-flash        429（已用盡）
gemini-flash-latest     429（別名，同一個桶）
gemini-3.6-flash        200
gemini-3-flash-preview  200
```

備援因此改為一條鏈：`gemini-3-flash-preview` → `gemini-3.6-flash` →
`gemini-flash-latest`。前兩個是真正不同的模型，各有自己的額度；
最後那個是別名，配額用盡時幫不上忙，但在「主要模型退役」時它是唯一保證有效的目標，
所以留在最後當安全網。觸發換模型的條件也從只看「模型不可用」擴大到包含
「配額用盡」與「逾時或忙碌」。

**順序依實測速度排，不是依版本新舊。** 同一份請求在正式環境的耗時
`gemini-3-flash-preview` 為 12 至 15 秒、`gemini-3.6-flash` 為 32 至 48 秒。
預算只有五十餘秒，快的排前面直接把逾時率從一半降到接近零。
結構由 responseSchema 保證，不同模型的差異只在敘述風格。

實際使用的模型會回傳並顯示在畫面上。敘述的風格與品質會因模型而異，
默默換掉會讓人以為是同一個模型的輸出不穩定。

錯誤訊息也一併修正：原本寫「請稍後再試」，但每日配額要等隔天才會重置，
那句話只會讓使用者一直重按。現在明講是今日額度用盡，並提醒程式計算的區塊不受影響。

### 額度

一檔要打五個 FinMind 資料集，註冊層的上限是 600 requests/hour。
財報一季更新一次、月營收一月一次，因此 `TTL.FUNDAMENTAL` 設為 24 小時，
前端也只在該檔尚未載入時才取用。

ETF 沒有財報與月營收，`missing` 會列出缺哪幾項——這不是錯誤，
介面據此顯示「屬正常情形」而不是「載入失敗」，並且仍會顯示它的配息紀錄。

## 績效計算

`src/lib/performance.js` 先建出每日權益曲線，日、週、月、年的損益與報酬率全部由這條曲線推導，
不各自獨立計算。這樣可以保證各時間尺度互相一致，不會出現月損益加總不等於年損益的情況。

```
當日損益 = 當日淨值 - 前一日淨值 - 當日淨入金
```

扣掉淨入金是必要的，否則匯入一筆資金會被當成獲利。

### 兩種損益定義，用在不同地方

**成本法**（總損益、未實現損益、總淨值）

```
總損益 = 已實現損益 + 未實現損益
未實現損益 = 目前市值 - 總成本
```

不受起算日影響，這是使用者真正在意的「賺多少」。由 `positionSummary()` 計算，
持股頁與績效頁共用同一個函式，兩頁的市值、未實現損益與總淨值不可能出現分歧。
先前兩頁各自計算，績效頁用權益曲線的收盤價、持股頁用即時報價，盤中會顯示不同的總淨值。

**淨值變動法**（每日損益月曆、每月走勢、歷年績效）

時間序列只能用淨值相減產生，成本法做不出每日數列。但它有一個必須讓使用者知道的性質：

```
區間累計 = 今日市值 - 起算日市值
```

**完全不看成本。** 直接輸入既有部位時，起算日是持股的建倉登記日，
登記日之前的獲利不存在於曲線中。若登記當天行情比現在高，這個數字還會變成負數。

實測同一組部位（未實現損益固定 20,000）在不同登記日的曲線累計：

| 建倉登記日 | 曲線累計 |
|---|---|
| 2026-01-02 | +40,000 |
| 2026-06-02 | -30,000 |
| 2026-08-17 | 0 |

因此績效頁的頭部數字改用成本法的「總損益」，曲線的累計值移到月走勢區塊並標明起算日。
當月損益若只涵蓋部分月份，會顯示「僅涵蓋 YYYY-MM-DD 起」而不是讓人誤以為是整月。

### 統計起算日

直接輸入既有部位時，權益曲線預設從「登記進系統那天」算起。但若持股在更早之前就已買進
且之後沒有異動，曲線其實可以正確回推——**持股數固定，缺的只是每日收盤價，而那是可以取得的**。

績效頁的「統計起算日」就是為此而設。設定後，沒有交易紀錄的持股會以該日作為建倉日，
每日損益月曆與當月損益即可涵蓋完整期間。留空則各持股沿用自己的建倉日。

起算日設在年中時，歷年績效那一列並非整年，表格會加註「自 MM-DD 起」，
避免被誤讀成全年報酬。

區間的第一天會跟「區間前一個交易日」的收盤價相比，不是歸零。起算日設 8/1 時，
8/3 是第一個交易日，它相對 7/31 收盤的漲跌仍然算進當月損益。
只有在歷史股價本身就從第一天才開始（沒有前一日可比）時，第一天才會是零。

### 除權息不能算成虧損

歷史股價取的是未還原的原始收盤價。除息當天股價會直接跌掉配息金額，
若只看價差，那一天會憑空多出一筆等於配息的虧損——而錢其實是進口袋的。

`/api/history` 因此一併帶回除權息資料，權益曲線在除息日把「持股數 × 每股配息」
計入現金，當天的價格缺口正好被抵銷。

持有高股息 ETF 時這個差距不小。以持有十七檔 ETF 的實際部位為例，
2026-08-18 一天六檔同時除息就造成一萬六千餘元的假性虧損，一整年的量級是十萬起跳。

兩個必須知道的性質：

1. **採除息日應計，不是入帳日。** 現金實際入帳約在除息後一個多月，因此曲線上的
   歷史現金會比對帳單早認列這筆錢。損益數字不受影響（前後兩天同樣偏移，相減後抵銷），
   但歷史現金水位會偏低。「歷史現金為負」的警示因此會把累計配息加回再判斷，
   否則單純因為配息就會誤報。
2. **只涵蓋現金股利。** 股票股利（無償配股）會讓股數增加，需要自行補一筆交易紀錄。

### 為什麼近期股價不採用 Yahoo

歷史 K 線主要來自 Yahoo，但**最近三個交易日的收盤價一律改用證交所與櫃買的官方行情**，
除權息也以官方的除權除息計算結果表為準。原因是 Yahoo 對台股 ETF 有三種各自獨立的錯誤，
而且都不會自己浮現：

| 症狀 | 實例 | 後果 |
|---|---|---|
| 收盤價缺值 | 2026-08-17 的 0056、00878、00403A 等九檔 `close` 為 `null` | 該日損益變成零，隔日承擔兩天漲跌 |
| 收盤價錯值 | 2026-08-17 的 00940，Yahoo 12.54，證交所 12.46 | 當日與隔日的損益各錯一段 |
| 除權息事件落後於價格 | 2026-08-18 六檔 ETF 除息，收盤價已扣除，事件表尚無該筆 | 憑空多出等於配息的虧損 |

證交所在除息當天就會公布，且收盤行情是法定資料，這三件事都只有官方來源能解決。

**盤中不查今天。** 官方收盤行情要等收盤後才公布，盤中查今天必然是空的，
而空結果會被標成不完整、只快取一分鐘，於是每分鐘重抓一次全市場行情——
純粹的浪費，也是最容易讓整個請求逾時的一段（實測會造成 `504`）。
今天那根 K 棒在權益曲線裡本來就會被即時報價覆蓋，根本用不到官方值。

只校正最近三天是成本考量：每多一天就要多打一次上游，且每次回應都是全市場上千列。
更早的資料 Yahoo 通常已經補正確，且逐日分配對舊資料的意義也較低。
這些請求逾時設短且不重試——校正不到只是少一層修正，讓整個請求逾時卻是完全沒有資料。

上市與上櫃分開查也分開快取。只持有上市股時不必去打櫃買，而且櫃買掛掉時
上市的結果不會跟著被標成不完整、每分鐘重試一次。

### 歷史股價缺了交易日會安靜地算錯，因此自動重抓

這是實際踩到的缺陷，症狀極具誤導性：**同一個帳號，桌機顯示的每日損益與手機不同。**

實例：9/17 的「今日各檔損益」是 28,988，月曆那格卻是 27,088；9/16 那格也不對。
手機兩個數字一致。

成因鏈：

1. 兩個數字的口徑不同源。今日損益用即時報價的漲跌（現價 − MIS 昨收），
   月曆用「現價 − 歷史 K 線的前一交易日收盤」。
2. 正常情況兩者相等。但若某一檔的歷史 K 線缺了 9/16 那根，月曆的基準會退回 9/15 收盤，
   於是 9/16 少算它的漲跌、9/17 用錯誤的基準計算。
3. 歷史股價前端一天只抓一次（`isHistoryStale` 只看日期）。抓到殘缺回應的那台裝置
   **整天都不會再重抓**，另一台正常，兩台因此顯示不同數字。

兩層修正：

**伺服器端第一層：用官方月報表把 Yahoo 整根缺掉的 K 棒補回來。**

原本只用官方資料**校正已經存在的那幾列**。Yahoo 給 `null` 收盤時校正後就有值，
但它也會**整根不回傳**，那種情形校正碰不到，那一天就永遠不存在。

實測 2026-09-29：`0056`、`00713`、`00878`、`00891`、`00900`、`00904`、`00915`、
`00919`、`00929`、`00940`、`00944`、`00403A` 等**十五檔 ETF** 在 Yahoo 的序列裡
沒有那一天，而證交所的月報表有。而且重抓完全無效——Yahoo 每次都給同一份缺漏的資料，
所以前端自動修復跑完兩輪仍然顯示「缺漏」。這與 2026-08-17 那次是同一批 ETF，
屬於 Yahoo 對台股 ETF 的慣性缺漏，不是偶發。

官方月報表本來就已經抓回來了，拿它補洞不需要任何額外請求。兩道界線：

- **不補今天。** 今天在權益曲線裡一律以即時報價評價，補了也用不到；
  而盤中官方月報表還沒有今天那列，本來就補不了。
- **不補早於 Yahoo 序列起點的日期。** 官方資料涵蓋最近三個月，`range=1mo` 時會比
  Yahoo 的區間更長，補進去等於擅自延長查詢範圍。`missingPastDays` 的計數也套用
  同一道界線，否則短區間查詢會永遠被判為不完整而只快取一分鐘。

補上的那一根成交量留 `null`：官方月報表的成交量欄位在上市與上櫃的單位不同
（股與仟股），為了一根 K 棒去處理那個單位陷阱不值得。損益完全不用成交量，
只有量能比會受一天影響。

**伺服器端第二層：官方也補不了時，把「整根沒回傳」算成缺漏。** 原本的
`missingPastDays` 只看得到「有這一列但收盤是 `null`」。補洞之後剩下的缺漏就是
官方月報表那一趟也失敗的情形，那種回應必須標成不完整（只快取一分鐘），
才不會被抓到它的裝置留用一整天。官方那一趟失敗時無從判斷，計數為零，不誤報。

**前端：偵測到缺漏就自動重抓，不必等使用者發現頁面下方的警告。**
重試上限 2 次，理由有兩個：

- 沒有上限就是無限迴圈。重抓完成後 `history` 更新，偵測若仍成立就會再觸發一次，
  而上游真的沒有那幾天時，這個迴圈永遠不會停。
- 取 2 而不是 1，是因為伺服器端有多個 serverless 實例、各自有獨立的記憶體快取。
  第一次抓到殘缺資料的那個實例未必是第二次服務的那個——這正是同一時間手機正確、
  桌機錯誤的成因，也是重抓有效的原因。

還有重試配額或請求進行中時顯示「正在自動重新載入」；用完仍缺才顯示琥珀色警告，
因為那代表上游真的沒有這幾天，數字確實不可信，使用者需要知道。

#### 偵測必須排除今天，否則是大規模假警報

自動修復上線後實際遇到的：一次報 **16 檔**「已自動重新載入 2 次仍然缺漏」。
成因不是上游缺資料，是偵測本身。

今天那根 K 棒不是同時到齊的。Yahoo 對台股 ETF 的當日收盤常給 `null`，那種列會被
伺服器濾掉；正常交易的個股有值、會保留。於是「所有標的的日期聯集」含有今天，
**沒有今天那根的標的全部被判為缺漏**。持有十幾檔 ETF 加幾檔個股時，形狀完全吻合。

而且這種警報既無意義也修不掉：

1. **無意義**——今天那根 K 棒在權益曲線裡從頭到尾用不到，一律以即時報價評價
   （`buildEquityCurve` 的 `liveDate`）。缺它不影響任何數字。
2. **修不掉**——重抓也拿不到上游還沒發布的當日收盤。自動修復只是白跑，
   而 16 檔 × 2 次 × 兩年份正是前面記載過把 `/api/history` 打到 `504` 的請求形狀。

因此偵測只看「今天以前」的日期。昨天以前不排除：那些 K 棒確實會被用到，
缺了就是真的會算錯。自動修復另外加了單批上限 5 檔，避免任何原因造成的請求風暴。

修正前後以三種形狀驗證：只缺今天由 16 檔降為 0 檔；「5 檔同缺 09-26」與
「尾端落後停在 09-25」兩種真缺漏仍照實偵測。

### 快取必須合併進行中的請求

績效頁一次會查數十檔個股，每一檔都要用到同一份除權息表與同一天的收盤行情。
只看「快取有沒有命中」是不夠的：快取要等 producer 完成才會寫入，
在那之前抵達的請求全部會撲空並各自再跑一次 producer。

實測是 28 檔 × 3 天 = 84 次全市場查詢同時發出，函式直接逾時，前端只看到 `504`。
`withCache` 與 `withPartialCache` 因此都加上進行中請求的合併：同一把鑰匙只會有
一個 producer 在執行，其餘請求共用那個 promise。

修正後 28 檔並發的實測是冷啟動 1.6 秒、快取命中 0.06 秒。

**這個陷阱對任何「多個請求共用同一份重量級上游資料」的設計都成立**，
新增這類共用資料時要記得走這兩個包裝器，不要自己寫一份只查快取的版本。

### 刪除必須靠墓碑，不能靠聯集

雲端合併原本是純聯集：`mergeById(local, cloud)` 取兩邊的並集。
這讓**刪除完全無法傳遞**——使用者刪掉一筆，雲端那份還在，
下次開啟合併時又被加回來，症狀是「清除了，每次重開又出現」。
這對持股、追蹤標的、交易與資金流水一律成立，不只是交易紀錄。

因此改為記錄刪除這個動作本身。`portfolio.deleted` 是
「集合名稱 → 鍵 → 刪除時間」的對照表，合併時據以濾除。
追蹤標的與持股以代號為鍵，交易與資金流水以 id 為鍵。

三個必須注意的地方：

1. **墓碑要與項目自身的建立時間比較，不能只看有沒有墓碑。**
   刪掉一檔後又重新買進時，本機雖已撤掉墓碑，雲端那份還在，
   兩邊聯集後墓碑復活，剛加回來的持股就會被濾掉——
   症狀是「新增後重開又不見了」，與原本的問題剛好相反。
   `addedAt` 晚於刪除時間就代表這是新的一筆，墓碑不適用。
2. **項目因為較新而留下時，要一併清掉那個墓碑**，否則它會一直掛在資料裡，
   讓人以為刪除還在生效。
3. **墓碑會過期。** 保留九十天後清除，避免無限累積。
   代價是離線超過這麼久的裝置回來時，它手上的舊資料會被當成新資料合併回來。
4. **「清除某幾檔的全部進出紀錄」要記成代號層級，不能只記 id。**
   清除當下只看得到本機那幾筆，雲端若還有同一檔的其他 id
   （來自另一台裝置或更早的工作階段），就不在名單裡，合併時照樣回來——
   症狀還是「清除了又出現」。因此另外記一份 `transactionCodes`：
   「這一檔在某個時間點之前的紀錄全部刪除」。交易也因此需要 `addedAt`，
   清除之後才記的交易才不會被一併濾掉。

合併邏輯因此獨立成 `src/store/merge.js`：它全是純函式，不碰 Firebase 也不碰
localStorage，可以直接在 Node 執行測試。合併規則出錯的後果是資料悄悄變多或變少，
必須能單獨驗證。

### 股數要以持股清單為準

權益曲線的股數是由交易紀錄逐筆累加，持股頁則直接採用持股清單。
**兩者只要不一致，兩頁就會各說各話，而且完全沒有跡象**——持股頁的市值仍然正確，
績效頁的每日損益卻整段等比例偏離。實際遇到的是同一批交易被匯入兩次，
每日損益因此變成大約兩倍。

持股清單是使用者直接維護、也是持股頁採用的來源，可信度較高，因此以它為準：
`reconcileShares()` 算出每檔的差額，補進期初部位，
讓曲線的終點股數必然等於持股清單。同時在績效頁列出不符的標的，
因為交易紀錄本身仍然是錯的——已實現損益、平均成本都會受影響，得由使用者修正。

這與「持股頁與績效頁共用 `positionSummary()`」是同一個原則：
**同一個數字只能有一個來源，不一致時要當場講出來，不能默默各算各的。**

兩邊分家的來源是 `recordTrade()`：新增持股一律會留下一筆買進紀錄，
但 `updateHolding()` 讓使用者直接改股數卻不會更新那筆紀錄。
重複輸入同一檔也會多留一筆。**而介面上沒有任何列出這些紀錄的地方**，
使用者看到警示也無從自行修正——因此警示附帶
`dropTransactionsForCodes()` 的一鍵清除，只影響指定標的的進出紀錄，持股本身保留。
清掉之後該檔改用「以統計起算日建倉」的補記方式，股數與成本直接取自持股清單。

用詞上刻意稱為「進出紀錄」而不是「交易紀錄」：使用者不認為輸入既有庫存算是一筆交易，
用「交易」講他們會找不到對應的東西。

### 月曆的今天要跟「今日損益」同一個口徑

歷史 K 線在前端整場快取，盤中不會重抓，今日那根 K 棒因此停在開頁當下的價格；
而「今日損益」用的是每次重新整理都會更新的即時報價。兩者同源不同時點，
盤中一定會愈差愈遠。

`buildEquityCurve()` 因此接受 `quotes` 與 `todayDate`：**曲線最後一天若就是今天，
改以即時報價評價**。除息日兩者仍然一致——即時報價的昨收是除息參考價，
而曲線的基準是「原始昨收 − 配息」，兩者相等。

### 歷年累積報酬採逐年連乘

```
累積報酬 = Π(1 + 各年度報酬率) - 1
```

不用「累計損益 ÷ 某個基準」。各年度的資本規模本來就不同（本金會增減資），
跨年的累計損益除以任何單一基準都會失真。連乘是標準的時間加權做法，
增資也不會把報酬率灌水或稀釋。

### 三個實作上的取捨

1. **歷史現金由目前餘額往回推算**，而不是從零累加交易紀錄。使用者填的「帳上現金」是實際餘額，
   可信度高於由可能不完整的交易紀錄累加出來的結果。若推算出的歷史現金曾為負值，
   代表現金與交易紀錄對不起來（通常是漏記入金），介面會直接提示。
2. **曲線起點為帳戶成立日**，不是歷史股價的起點。歷史股價預設抓兩年，比帳戶存在的時間長，
   若從股價起點開始算，那段期間的現金會因為往回推算而變成負值，淨值與年度報酬會完全失真。
3. **年度報酬率的分母未做時間加權**，採「年初淨值加該年淨入金」。嚴謹做法應以入金時點加權，
   但那需要更完整的資金流水；目前的簡化版本在年中有大額入金時會低估報酬率，介面上已註明。

### 成本均價的定義

記錄交易時填入的價格是**已含手續費與交易稅的單位成本**，也就是券商對帳單上的成本均價，
程式原樣採用，不會再自行加計費用。

早期版本是讓使用者填純成交價、由程式自動加上手續費，但那樣算出的均價和券商對帳單對不起來，
而且小額交易會因為手續費有最低 20 元的規定被明顯墊高（買 100 股 30 元的個股，均價會被推高 0.67%）。
改由使用者填入實際數字，數據來源單一且可對帳。

輸入欄位接受小數點後四位，顯示時取兩位。已實現損益採平均成本法。

`src/lib/fees.js` 仍保留台股費率計算（券商手續費 0.1425% 打六折、最低 20 元、
一般股票證交稅 0.3%、ETF 證交稅 0.1%），但只用於表單下方的**參考試算**，
供手邊沒有對帳單時自行換算含費用成本，不會寫入任何記錄。

## 籌碼面

`src/lib/chips.js` 由 FinMind 的每日買賣超序列計算連續買賣天數與區間累計。

連續天數的判定規則：從最近一個交易日往回數，方向相同才續計，**買賣超為零的當天視為中斷**。
把「當天沒有動作」算進連買會虛增天數，那個數字用來判斷法人態度就失去意義。

法人別的歸類需注意順序。FinMind 回傳五種法人別：`Foreign_Investor`、`Foreign_Dealer_Self`、
`Investment_Trust`、`Dealer_self`、`Dealer_Hedging`。其中 `Foreign_Dealer_Self` 同時符合
外資與自營商兩種樣式，而市場慣稱的「外資」包含外資自營商，因此必須先判定外資再判定自營商。

圖表的三個法人別堆疊在同一根柱子上，`stackOffset="sign"` 讓正負值分別往上下堆疊而不互相抵銷，
整根柱子的高度即為三大法人合計。顏色刻意避開紅綠：在台股語境紅綠代表漲跌，
用在法人別上會被誤讀成「紅色那個是買超」，但柱狀圖的正負才是買賣方向。

## AI 型態分析

### 分工原則：價位由程式算，模型只負責解讀

參考站的做法是把 K 線丟給模型，要它直接輸出「第一支撐價位」這類數字。這有風險：
語言模型對長數列做精確數值推理並不可靠，可能給出看似合理、但不落在任何轉折點或
量能密集區的價位。那種數字拿來設停損沒有依據。

本專案改為分工：

- **價位由 `src/lib/levels.js` 計算**，來源有四種，每個價位都可逐項驗證
  - 擺盪轉折點：以碎形定義找出價格實際反轉過的位置
  - 成交量密集區：把價格區間分帶，統計各價格帶的換手量
  - 移動平均線：20、60、120 日
  - 區間極值：統計期間的最高與最低
- **模型只做敘述**：辨識型態、解讀各價位的意義、推演突破與跌破的情境

系統提示明確禁止模型產生或修改任何價格數字，只能引用提供的價位。介面上也把
程式算出的價位與模型的敘述分開呈現，方便查核。

價位會先做群聚合併，避免同一價格區域的多個轉折點被當成好幾個獨立支撐。
強度分數由來源權重、歷史觸及次數與時間近因構成。

### 短中長線立場

三個週期各自對應不同的資料，提示詞明確指定不得跨週期硬推：

| 週期 | 期間 | 判斷依據 |
|---|---|---|
| 短線 | 數日至兩週 | KD、MACD、5 日乖離、量能比、最近支撐壓力距離 |
| 中線 | 數週至數月 | 20 與 60 日均線關係、型態、法人近 5 日與近 20 日買賣超、融資融券 |
| 長線 | 數月以上 | 120 日均線方向與斜率、現價在區間中的位置、本益比、股價淨值比、殖利率 |

立場以列舉限定為偏多、偏空、中性、觀望四種，介面才能據此上色。
開放自由文字會出現「偏多但需觀察」這類無法歸類的值。

**輸出的是技術面狀態，不是買賣指令。** 系統提示禁止出現具體的買賣指令、目標價、
停損價與部位配置比例，也禁止「建議買進」這類祈使語氣。

資料缺漏時要求模型如實說明。實測刻意不提供籌碼與估值資料時，模型會寫出
「籌碼面缺少法人與融資券資料，依據不足故維持中性」，而不是拿技術面硬推中線立場。

### 送出的內容

`src/lib/analysisInput.js` 只送價位結構、指標快照、近期走勢摘要、估值與籌碼摘要，
實測約 1.2 到 1.7 KB，不送完整 K 線序列。
除了省流量，更重要的是不給模型從數列裡自行挑價格的機會。

### 輸出格式

透過 Gemini 的 `responseSchema` 強制結構化輸出，而不是在提示詞裡請模型「回傳 JSON」。
後者在模型偶爾多加一段說明文字時就會解析失敗。

### 模型選擇與退役處理

預設 `gemini-3.7-flash`，實測單次分析約 6 到 10 秒。

Google 會讓舊模型進入「仍列在模型清單中，但對新使用者回傳 404」的狀態。
實測 `gemini-2.5-flash`、`gemini-2.5-pro`、`gemini-2.5-flash-lite` 都是這個情況，
光呼叫 `listModels` 看不出來，要實際送出請求才會失敗。

因此 `gemini.js` 在遇到模型不可用的錯誤時會自動改用 `gemini-flash-latest` 這個別名重試，
把硬性中斷變成可用的降級。

### 金鑰安全

金鑰只存在伺服器端環境變數，前端 bundle 與網路請求的網址中都不會出現。
參考站是讓使用者把金鑰貼進網頁並存在 localStorage，那等於把金鑰暴露在瀏覽器裡。

### 如何查核模型有沒有捏造價格

把模型輸出的所有文字合併，抽出價格量級的數字，逐一比對是否出現在送出的提示詞中
（價位清單、均線值、ATR、期間高低點）。任何對不上的數字都代表模型自行產生了價格。

注意允許清單要涵蓋提示詞中的**所有**價格量級數字，不只價位清單。指標區塊的均線值、
ATR 與期間高低點也是合法引用來源，只比對價位清單會把合法引用誤判為捏造。

同時查核立場是否落在允許的列舉值，以及有沒有出現被禁止的買賣指令表述。

實測 2330 與 6488 三項查核皆通過。介面上也把程式算出的價位與模型敘述分開呈現，
使用者可自行對照。

## 資料自動更新

三處定時更新，全部走 `src/lib/useMarketPolling.js`：

| 位置 | 間隔 | 內容 |
|---|---|---|
| `Header` | 5 分鐘 | 報價與每日資料，四個分頁都受益 |
| `AnalysisTab` | 30 秒 | 自選股報價 |
| `MarketIndices` | 60 秒 | 加權與櫃買指數 |

原本只有後兩者，而且是裸用的 `setInterval`。兩個問題：

1. **持股頁、績效頁、AI 頁完全沒有自動更新。** 開著持股頁看市值，數字可以一整天不動，
   畫面上也沒有任何跡象顯示那是幾點的資料。`Header` 一直掛載，把更新放在這裡即可覆蓋全部分頁。
2. **裸用的 `setInterval` 永遠不會停。** 分頁整晚不關，30 秒的輪詢就是每天約 2,880 次請求，
   其中絕大多數打的是收盤後不會再變的數字；手機把分頁丟在背景也照打。

因此共用 hook 加兩道閘門：分頁不在前景就跳過，不在交易時段就跳過。
回到前景時補一次，但距上次更新未滿一個間隔就不補，否則在分頁之間來回切換
會變成每切一次打一次。

**首次取得資料不設閘門**，由各元件自行負責。開頁時就算是半夜，也該把最後一次收盤的
數字顯示出來——這與「後續要不要繼續更新」是兩個問題。

### 交易時段的判定

`src/lib/marketHours.js` 判定週一至週五 08:30 至 18:00，**一律以台北時間計算**。
用裝置本機時區的話，使用者在國外會整個判錯，而症狀是「畫面數字整天不動」，
從介面完全看不出原因，會被當成程式壞掉。

終點取 18:00 而非 13:30 收盤：融資融券、三大法人、估值都是收盤後才陸續發布，
那段時間的更新正是把當日數字補齊的時機。

只看星期與時間，**不判斷國定假日與颱風假**。要精準就得維護交易日曆還要處理補班日，
成本與效益不成比例；判錯的代價只是假日多打幾次，而那些請求本來就有伺服器快取擋著。

### 配套：標題列顯示「報價更新於 HH:MM」

有了自動更新之後，「資料是什麼時候的」變成必須看得到的資訊。非交易時段會跳過更新，
數字停著不動是正常行為，少了時間戳就分不出那是正常還是壞掉。與原本的標語共用同一行。

## 新版本偵測

`index.html` 設定為每次重新驗證，但使用者若一直開著分頁不重新整理，就永遠拿不到新版，
還會誤以為修改沒有部署。

建置時 `vite-plugin-version.js` 把同一個識別碼寫進兩個地方：

- 編譯進 bundle 的 `__BUILD_ID__`，代表「手上這份程式碼是哪一版」
- `dist/version.json`，代表「伺服器上目前是哪一版」

前端比對兩者，不同就顯示提示列。識別碼在 Vercel 上取 commit SHA 前 12 碼，本機建置取時間戳。

檢查時機是載入時、每 5 分鐘一次，以及分頁重新回到前景時。最後一項最重要：
使用者放著分頁好幾天再回來看是最常見的情境，只靠定時檢查會讓他先看到舊畫面。

**不自動重新載入**，因為使用者可能正在輸入交易紀錄，突然重整會讓輸入到一半的內容消失。
提示列可以關閉。

`vercel.json` 的 SPA 轉址規則明確排除 `version.json`。平台雖然會先比對檔案系統，
但若順序改變，版本檢查會拿到 `index.html` 而解析失敗，且是靜默失敗、不會有人發現。

注意 `vercel.json` 採嚴格結構驗證，**不可加入 schema 未定義的欄位**（例如自製的 `_comment`），
否則整個部署會失敗，而 GitHub 上只會顯示「Deployment failed」，不會指出是哪一行。
JSON 本身也不支援註解，說明一律寫在這份文件裡。

## 部署

推送到 GitHub 後於 Vercel 匯入專案，框架選 Vite，並在專案設定中加入環境變數
（`VITE_FIREBASE_*` 與 `FINMIND_TOKEN`）。`vercel.json` 已設定好 SPA 轉址規則與 API 路徑排除。

部署後記得到 Firebase Authentication 的授權網域加入 Vercel 網域，否則登入會失敗。
